# Feature: call-level-taint
Objective: detect personal and health data reaching log sinks through variables and function calls (call-level data flow), and prove against the labelled corpus whether it improves on the current detectors.
Branch: `feat/call-level-taint` (from `chore/harness-cleanup` at `b15abb3`). Delivery: ask-on-risk. Test runner: `python -m pytest tests -q -p no:cacheprovider`.

## Specs

- **S1 — Call-level data flow to sinks.** "pensaba que ibamos a usar el motor de grafo para analizar estaticamente el flujo de datos en el codigo en base a sus llamados y dependencias y detectar sus sumideros de informacion". Scope: Python, CWE-532 log sinks (the `privacy.cwe_532` policy), flow through assignments, containers, return values and calls resolved by name within the evaluated files. The finding keeps the policy id `privacy.cwe_532`, so the pre-commit gate and the pack mapping do not change.
- **S2 — Prove the improvement.** "eso como podemos comprobar que mejoraria nuestro harness?" and "procede con el desarrollo de eso entonces". Acceptance: on the labelled corpus, compare three detectors on the same log cases: the current local AST detector, the existing file-level lineage engine (`DataLineageEngine`, as the control), and the call-level detector. The call-level detector improves the harness only if it raises recall on flow cases and keeps zero false positives on clean cases. Assumption: the harness-level experiment B (T7 of `harness-consolidation`) is out of this feature; it stays the place where the oracle is independent of this detector.
